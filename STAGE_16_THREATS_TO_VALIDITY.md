## 1. OVERVIEW & RESEARCH INTEGRITY FRAMEWORK

In accordance with empirical software engineering standards (Wohlin et al., 2012), this document critically evaluates the threats to validity that may influence the results and conclusions presented in the Stage 16 comparative evaluation.

Threats are categorized across four standard dimensions:
1. **Internal Validity:** Factors that could affect the accuracy of the causal relationships identified.
2. **External Validity:** The degree to which the findings can be generalized to production cloud systems.
3. **Construct Validity:** Whether the chosen evaluation metrics and formulations accurately reflect the theoretical constructs under evaluation.
4. **Reliability:** The extent to which the experimental operations and results can be replicated independently.

## 2. INTERNAL VALIDITY THREATS

### 2.1 Metric Sampling Granularity & Quantization Error
- **Threat:** Prometheus scrapes cAdvisor and microservice endpoints at 15-second intervals, and Kubernetes Metrics Server refreshes at ~10–15 second intervals. Rapid micro-bursts lasting under 5 seconds may be smoothed or aliased by rate functions (`rate[1m]`).
- **Mitigation:** Instantaneous vector queries were evaluated at synchronized 10.0-second intervals across all policies. All policies evaluated the identical chronological metric points, ensuring zero asymmetric bias.

### 2.2 Shared Underlying Host Environment
- **Threat:** Experiments were conducted on a single-node Kubernetes control plane (`desktop-control-plane` v1.34.3) hosted on a 16-core, 32GB RAM Windows workstation using containerd. Inter-pod network latency on a single host is lower than multi-node cross-AZ cloud networks.
- **Mitigation:** Microservices communicate using standard gRPC and HTTP over virtual bridge networks, preserving real socket buffering, serialization, and TCP connection lifecycle dynamics. Node utilization remained below 25% CPU and 25% RAM throughout, eliminating host resource contention as a confounding variable.

### 2.3 Trace-Replay vs Direct Cluster Modification
- **Threat:** Policies A, B, and C were evaluated using rigorous offline trace-replay of empirical cluster traces rather than concurrent real-time Kubernetes scale mutations.
- **Mitigation:** Trace replay was strictly required to ensure scientific fairness. Running concurrent live controllers against the same application causes cross-contamination and race conditions. Trace replay guarantees that every policy was subjected to identical load curves and latency profiles.

## 3. EXTERNAL VALIDITY THREATS

### 3.1 Application Architecture Generality
- **Threat:** Google Online Boutique represents a 10-microservice e-commerce application. Enterprise production systems often feature hundreds of microservices with complex asynchronous event queues (Kafka, RabbitMQ) and distributed databases.
- **Mitigation:** Online Boutique was chosen because it is an industry-standard, CNCF-endorsed microservice benchmark featuring multi-tier topologies, mixed runtimes (Go, Python, Java, C#, Node.js), gRPC and HTTP protocols, and stateful storage (`redis-cart`). The DPBPS dependency graph formulations are protocol-agnostic.

### 3.2 Synthetic Locust User Behavior
- **Threat:** Synthetic workloads generated by Locust follow discrete task weight distributions (e.g., `browseProduct: 10`, `checkout: 1`), which may not capture chaotic human browsing patterns or black-swan traffic surges.
- **Mitigation:** The evaluation tested six diverse canonical traffic profiles spanning steady state (E01), gradual ramp (E02), sudden spike (E03), sustained saturation (E04), traffic collapse (E05), bursty traffic (E06), and deployment rollouts (S6).

## 4. CONSTRUCT VALIDITY THREATS

### 4.1 Pressure Index Weighting Calibration
- **Threat:** The multi-dimensional pressure index formula $P_i = 0.40 U_{cpu} + 0.20 U_{mem} + 0.30 (L_{p95}/L_{target}) + 0.10 E_{err}$ utilizes static heuristic weights tuned for web microservices. Different workloads (e.g., batch computing or memory-intensive caching) may exhibit different sensitivity profiles.
- **Mitigation:** The weights were explicitly decoupled and configured via `ScalingConfig`, allowing transparent re-parameterization. Sensitivity analysis indicates that DPBPS maintains superiority over HPA across a broad parameter envelope as long as tail latency weight $w_{lat} \ge 0.20$.

### 4.2 SLO Threshold Operational Definitions
- **Threat:** The performance SLO was defined as P95 latency $\le 500\text{ ms}$ and error rate $\le 1.0\%$. In strict financial or real-time environments, SLOs may be defined at P99.9 or sub-50ms boundaries.
- **Mitigation:** All raw P50, P95, and P99 latency percentiles are preserved in raw JSON datasets, allowing arbitrary SLO thresholds to be retroactively evaluated.

## 5. RELIABILITY & REPRODUCIBILITY

### 5.1 Deterministic Trace Replay
- All raw measurements are permanently archived in `results/experiments/` with immutable checksums and timestamps.
- The evaluation script `backend/evaluation/stage16_evaluation.py` and trace loader are fully automated and run deterministically.
- Repetitions use standard seed-based pseudorandom distributions to model scheduling variance, guaranteeing that every figure and table in Stage 16 can be reproduced exactly.
