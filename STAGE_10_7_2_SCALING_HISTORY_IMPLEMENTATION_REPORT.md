## 2. Cluster Safety & Actuator Invariant Enforcement

The Scaling History page reinforces the platform's non-negotiable safety boundaries:

```
+------------------------------------------------------------------------------------------------+
| ACTUATOR SAFETY POSTURE: LIVE CLUSTER SCALING LOCKED [ SCALING_ENABLED=false ]                 |
| Recommendations generated by DPBPS are evaluated and audited against cluster bounds [1, 10]   |
| and step rate limits (|ΔR| ≤ 2). All actuation executes strictly in DRY_RUN simulation;        |
| zero Kubernetes scale patch mutations are executed.                                            |
|                                                                                                |
| Cluster Mutations: 0 pods             Logged Controller & Actuator Events: Audited & Reconciled |
+------------------------------------------------------------------------------------------------+
```

### Safety Invariants Enforced in UI:
1. **Zero Mutation Guarantee:** Prominent indicators verify that 0 live pod replicas have been modified in the `online-boutique` namespace.
2. **Explicit Actuator Mode:** Every logged event clearly denotes `DRY_RUN` execution status with a cyan shield icon.
3. **Safety Clamp Auditing:** Details drawer explicitly checks replica bounds ($1 \le R \le 10$) and rate delta step constraints ($|\Delta R| \le 2$).
4. **Fail-Closed Protection:** Telemetry-starved evaluations are classified as `INSUFFICIENT_TELEMETRY` and immediately held at equilibrium rather than guessing replica counts.

## 3. UI Component Architecture

The interface is structured into six functional modules adhering strictly to the Stage 10.2 design tokens (`#0b0f19` canvas, `#111827` cards, `#1f293d` borders, cyan/blue/emerald/amber/rose accents):

### 3.1 Actuator Safety Banner
- Positioned prominently below the page title.
- Outlines the exact safety posture: `SCALING_ENABLED=false`, `DRY_RUN=True`, cluster mutations: 0.

### 3.2 6-Card Operational KPI Grid
Interactive metric cards utilizing the centralized `MetricCard` component:
- **Total Decisions:** Total audited controller recommendations and actuator simulations.
- **Scale-Up Urgency:** Count of proactive or bottleneck-prioritized scale-up actions (`rose` variant).
- **Scale-Down Actions:** Traffic contraction recommendations, showing conservative dampening (`amber` variant).
- **Equilibrium Holds:** Resource utilization equilibrium cycles operating safely within bounds (`emerald` variant).
- **Insufficient Telemetry:** Telemetry gaps that safely fail-closed to hold (`purple` variant).
- **Cluster Mutations:** Strictly `0` pods, confirming locked live actuator status (`emerald` variant).

### 3.3 Action Classification Taxonomy Banner
An educational and operational reference grid defining the algorithmic classifications:
- `SCALE_UP`: Capacity expansion (+1 or +2 pods) prioritized by DAG centrality and bottleneck severity.
- `SCALE_DOWN`: Conservative contraction recommendation (strictly suppressed during `ACTIVE_DEPLOYMENT`).
- `HOLD`: Stable equilibrium; metrics remain within deadbands ($[40\%, 70\%]$ CPU).
- `INSUFFICIENT_TELEMETRY`: Missing or warmup metrics; safely holds current replica count.
- `SIMULATED (DRY_RUN)`: Actuator simulation verified against cluster bounds; 0 patches issued.
- `LIVE MUTATION`: Live scale patch execution (strictly locked in current mode).

### 3.4 Multi-Dimensional Filter Controls
- **Free-Text Search:** Case-insensitive search matching service name, reason text, phase, or action.
- **Service Selector:** Dropdown filtering by any of the 10 microservices.
- **Deployment Phase Selector:** Filtering by `ALL`, `NORMAL_OPERATION`, `PRE_DEPLOYMENT`, `ACTIVE_DEPLOYMENT`, or `POST_DEPLOYMENT`.
- **Decision Type Filter:** Quick-toggle pills for `ALL`, `SCALE_UP`, `SCALE_DOWN`, and `HOLD`.

### 3.5 Chronological Decision & Actuator Log Table
An 8-column high-density audit ledger:
- **Timestamp:** Formatted with human-readable localized time.
- **Microservice:** Service identifier with mono-spaced formatting.
- **Phase:** Deployment phase badge with phase-specific color coding.
- **Replicas (Cur → Prop):** Visual replica transition indicator with arrow formatting (`1 → 2`, `2 → 2`, etc.).
- **Action:** Color-coded status badge (`SCALE_UP`, `SCALE_DOWN`, `HOLD`, `INSUFFICIENT_TELEMETRY`).
- **Actuator Mode:** `DRY_RUN` badge with shield icon.
- **Status:** Execution outcome (`SIMULATED`, `SUCCESS`, `NOOP`).
- **Algorithmic Reasoning:** Truncated summary of mathematical derivation reasons; clickable to open the details drawer.

### 3.6 Slide-Over Decision Details Drawer
When any log row is clicked, an interactive slide-over drawer displays:
- **Decision Overview:** Event ID, timestamp, microservice, deployment phase.
- **Replica Transition:** Visual current vs. proposed replica comparison.
- **Actuator Execution Audit:** Mode (`DRY_RUN`), execution status, cluster modified status (`false`).
- **Algorithmic Derivation Rationale:** Full unabridged reasoning text explaining exactly why DPBPS triggered or withheld scaling.
- **Telemetry Snapshot at Decision Time:** CPU utilization, memory utilization, request rate (RPS), and P95 latency recorded when the decision was computed.
- **Safety Bounds Verification:** Explicit confirmation that proposed replicas comply with $[R_{min}, R_{max}] = [1, 10]$ and $|\Delta R| \le 2$.

### 3.7 Microservice-Level Scaling Activity Breakdown
A secondary table aggregating scaling statistics across all 10 microservices:
- Lists all Online Boutique services: `frontend`, `cartservice`, `productcatalogservice`, `currencyservice`, `paymentservice`, `shippingservice`, `emailservice`, `checkoutservice`, `recommendationservice`, `adservice`.
- Displays current pod replicas, total decisions, scale-up events, scale-down events, hold cycles, latest action, and timestamp.

## 4. Backend API Integration

The page integrates with five backend endpoints via `frontend/src/services/api.ts`:
1. `GET /api/v1/scaling/status` (`fetchScalingStatus`): Fetches simulation mode, dry run status, scaling enablement, and active deployment phase.
2. `GET /api/v1/scaling/decisions?limit=50` (`fetchScalingDecisions`): Retrieves chronological decision records generated by the DPBPS controller.
3. `GET /api/v1/scaling/actuator/history?limit=50` (`fetchActuatorHistory`): Retrieves chronological execution history from the scaling actuator.
4. `GET /api/v1/scaling/pipeline-evaluation` (`fetchPipelineEvaluation`): Provides aggregate counts for scale-up, scale-down, and holds.
5. `GET /api/v1/services` (`fetchServices`): Fetches the active service list and current replica counts.

*Unified Data Reconciler:* The component automatically merges controller decision records with actuator execution results into a unified chronological stream, ensuring that telemetry snapshots, controller intentions, and actuator execution status are correlated by service and timestamp.
